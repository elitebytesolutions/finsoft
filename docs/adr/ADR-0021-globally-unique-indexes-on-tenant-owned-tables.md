# ADR-0021: When a unique index on a tenant-owned table may omit `tenant_id`

**Status:** Accepted
**Date:** 2026-09-25

**Deciders:** Product Owner, Architecture Guardian, Database Guardian
**Authority:** LEVEL 1
**Supersedes:** [ADR-0003](ADR-0003-shared-database-multi-tenancy.md) in respect of Decision bullet 28 and Compliance bullet 110 **only**. ADR-0003 remains in force in every other respect; a permanent supersession scope notice at its head names the two provisions, per [README](README.md) §4.

## Context

ADR-0003:28 reads, without qualification:

> Every unique constraint on tenant-owned data is scoped by tenant: `UNIQUE (tenant_id, document_type, number)`, not `UNIQUE (number)`.

Three things are wrong with that sentence as an operative rule, and W1-001 is the first task to hit all three at once.

**It has no stated exception, and the codebase has always relied on one.** Every table in migrations 001–005 has a surrogate `uuid` primary key, which is a unique constraint on tenant-owned data not scoped by tenant. The exemption exists only in a comment in `database/tests/schema.spec.ts:199-205`, written by the test's author. A LEVEL 1 rule whose only carve-out is documented in a LEVEL 3 artefact is a rule whose meaning is set by whoever last edited a test. That is the authority table inverted, and it is the specific failure mode the ADR directory exists to prevent.

**Its stated harm is narrower than the real one.** The test comment justifies scoping as "one tenant's data constrains another's" — a tenant *choosing* an email, a code or a document number and being refused because a neighbour took it. That harm is real but it is the lesser one. The larger harm is that **unique index enforcement is not subject to row level security.** PostgreSQL checks the index across every row, including rows the current role cannot `SELECT`. A globally unique index therefore couples tenants in two ways RLS was chosen to eliminate: a `23505` on insert is a cross-tenant existence oracle that pierces the policy, and one tenant's row can make another tenant's insert fail. ADR-0003:61 accepts that isolation here is logical rather than physical, and ADR-0004 is what makes that acceptable; a globally unique index is a hole in ADR-0004's backstop, not merely an inconvenience to a tenant's choice of codes.

**It and its own compliance clause disagree.** ADR-0003:28 gives a leading-column example, ADR-0003:110 says a unique constraint must "include" `tenant_id`, and the test asserts the first column *is* `tenant_id`. ADR-0003:27 settles it for access-path indexes — `tenant_id` leads, never trails — and the same reasoning applies here: a trailing `tenant_id` in a unique key gives a global namespace for the leading columns, which is the thing being forbidden.

W1-001 (migration 005, sessions and rotating refresh tokens) proposes two globally unique indexes on tenant-owned tables and fails the ADR-0003:28 test on both. They are not the same case, and a rule that cannot tell them apart is not a rule.

## Decision

### 1. Surrogate primary keys are exempt, and the exemption is stated here

A single-column `uuid` primary key on a tenant-owned table is not a business uniqueness rule. It is surrogate identity, generated by `gen_random_uuid()`, carrying no tenant meaning and expressing no tenant claim. The tenant-scoped guarantee that matters is carried separately by the `UNIQUE (tenant_id, id)` key that ADR-0003:29 already requires so composite foreign keys can be written.

This is where that exemption lives from now on. `database/tests/schema.spec.ts` cites it rather than reasons it.

### 2. Every other unique index on a tenant-owned table leads with `tenant_id`, unless it passes all six conditions below

The governing condition is **necessity**, and it is deliberately hard to satisfy:

> **(N) The uniqueness is relied upon by a lookup that executes before a tenant context exists**, so a tenant-scoped constraint would be unenforceable at the moment it is needed. Establishing the tenant must be the *purpose* of the lookup, not an incidental consequence of it.

A diagnostic justification does not qualify. Neither does log quality, query convenience, report simplicity, or "the value is random anyway". **"The value is system-generated" is not a criterion** — it describes how a value is produced, not why a tenant-scoped constraint cannot do the job, and it is satisfied by any column with a `DEFAULT`.

Four mechanical conditions accompany it, each checkable against the live catalogue:

1. **Single column.** A multi-column globally unique index has no justification of this shape; if a second column exists, `tenant_id` can be the first.
2. **Shape-pinned high-entropy value.** The column carries a `CHECK` constraint anchoring it to a fixed-length random-value format of at least 128 bits — `^[0-9a-f]{64}$`, `^scid_[0-9a-f]{32}$`. Checkable from `pg_constraint`.

   **A CHECK PINS SHAPE, NOT ENTROPY, and the distinction is the whole reason this condition is not sufficient on its own.** `scid_` followed by 32 hex characters *chosen by the inserting code* satisfies the regex exactly as well as 128 bits of CSPRNG output does. Where the column can carry a `DEFAULT` that generates the value, entropy becomes a schema fact **for every insert that omits the column** — which is why `sessions.session_correlation_id` was given `DEFAULT ('scid_' || replace(gen_random_uuid()::text, '-', ''))` rather than being left to its CHECK.

   **A `DEFAULT` is not a guarantee, and an earlier draft of this paragraph overstated it in exactly the way the paragraph itself warns against.** A DEFAULT applies only when the `INSERT` does not name the column; an explicit column list overrides it, and `finsoft_app` holds `INSERT`. Measured against this schema:

   ```
   INSERT INTO sessions (…, session_correlation_id, …)
   VALUES (…, 'scid_deadbeefdeadbeefdeadbeefdeadbeef', …)   ->  accepted
   ```

   Thirty-two caller-chosen hex characters with no entropy at all, and `sessions_scid_shape` is satisfied. `id` (`DEFAULT gen_random_uuid()`) had the identical property.

   **A DEFAULT plus a withheld INSERT grant, however, IS a control** — and that pairing is condition 6. Once `finsoft_app` cannot NAME the column, the DEFAULT is the only path by which a value can arrive, and the entropy is mechanical rather than promised. Measured on migration 005 after the grant: naming `session_correlation_id`, `id` or `created_at` raises `42501`. So for a defaulted column the remainder is closed by the grant, not by a review gate.

   **Condition 5 carries the whole weight only where no DEFAULT can exist** — `refresh_tokens.token_hash`, because the application must compute the hash and the database must never see the raw value it is the hash of. An earlier revision of this paragraph said condition 5 closed the remainder "for a defaulted column as much as for an undefaulted one". That was true of the migration this ADR was drafted against and is no longer true of the one it admits.

   Where a DEFAULT is impossible — `refresh_tokens.token_hash`, because the database must never see the raw value it is the hash of — entropy remains an application promise, and condition 5 becomes load-bearing rather than ceremonial. **A requesting ADR must then name a test over the PRODUCTION MINTER**, not over a test fixture: a fixture that generates good values proves nothing about the code path that runs in production, and it is the production minter whose failure would make the index a live oracle.
3. **Write-once.** The column appears in no column-level `UPDATE` grant to `finsoft_app`, so its value can only be set at `INSERT`. Checkable from `has_column_privilege`. This is what makes "not caller-chosen" partly mechanical: a value nobody can update is a value nobody can steer into a collision after the fact.
4. **Named, with a reason and this ADR's number**, in `GLOBALLY_UNIQUE_INDEX_ALLOWLIST` in `database/tests/schema.spec.ts`. The test fails on an entry naming an index that does not exist, so a stale exemption cannot linger and be inherited by a later table that copies the pattern.

And two more. Condition 5 cannot be mechanised and is a review gate recorded in the ADR that requests the exemption; condition 6 is a catalogue assertion like conditions 1–4, and applies only where a `DEFAULT` is possible at all:

5. **The value is minted server-side from a CSPRNG, and no caller-supplied value is ever written to the column.** A caller-supplied value would make the `23505` oracle reachable, which is the whole reason conditions 2 and 3 exist.

6. **Where a `DEFAULT` is possible, the column appears in no column-level `INSERT` grant either**, so the `DEFAULT` is the only path to a value and its entropy is mechanical rather than promised. Checkable from `has_column_privilege`, exactly as condition 3 is for `UPDATE` — the two are twins, and an earlier revision of this ADR stated only the `UPDATE` half. Measured on migration 005: naming `session_correlation_id`, `id` or `created_at` raises `42501`.

   Where a `DEFAULT` is impossible — `refresh_tokens.token_hash` — this condition is unavailable, which is precisely why condition 5 carries the whole weight there and why its production-minter test is a gate rather than a formality.

An email address fails condition 2 on sight and condition 3 in practice. A tenant-chosen product code fails both. That is the point: the conditions are not a description of the two indexes in front of us, they are a filter that a business key cannot pass.

### 3. Applying it to migration 005

**`refresh_tokens.rt_token_hash_key` — permitted.** A refresh token arrives as a bare opaque value in a cookie with no tenant context; establishing the tenant is what presenting it is *for*. The lookup is `WHERE token_hash = $1` with nothing to scope by, so a `(tenant_id, token_hash)` constraint would be unenforceable at exactly the moment its guarantee is needed. Condition (N) is met in its strict sense.

The necessity is not merely about convenience of lookup. Under per-tenant scoping the same hash could legitimately exist in two tenants, so the by-hash lookup would have to tolerate multiple rows and the application would have to choose one. Choosing wrong on this path means marking the wrong token spent, or revoking the wrong family in the wrong tenant, in response to an unauthenticated request — a cross-tenant write, rule 8. Global uniqueness here is a safety property, not an optimisation. Conditions 1–3 are met by `rt_hash_shape` (`005:384-385`) and by the `UPDATE` grant at `005:751-752`, which omits `token_hash`.

**`sessions.sessions_correlation_key` — refused.** Its justification is that logs are aggregated across tenants and a collision would join two unrelated traces. That fails (N) in two independent ways.

The uniqueness is never relied upon before a tenant is known: a correlation id is minted at session creation, when the tenant is already established, and read from a log line, not looked up to discover a tenant. And the harm it claims to prevent is already prevented elsewhere — `CorrelationContext` carries `tenantId` alongside `sessionCorrelationId` (`packages/observability/src/context.ts:76,79`), and both are emitted on every line, so the join key in the aggregated store is already `(tenantId, sessionCorrelationId)`. The index buys the difference between a 128-bit collision and a failed login, at the price of a LEVEL 1 exception justified by diagnostic quality — which is the precedent a later author stretches.

ADR-0016 §5 does not require what is claimed of it. It says the identifier is "minted per session" and "random, not derived" (ADR-0016:106). It says nothing about a global namespace.

The index becomes `UNIQUE (tenant_id, session_correlation_id)`. The pairing that the log join now depends on is made structural rather than conventional: `sessionCorrelationId` may be set in a correlation context only where `tenantId` is also set, enforced in `withCorrelation`/`extendCorrelation` with a test. That is a better control than the index it replaces, because it asserts the property the logs actually rely on instead of a collision probability that stands in for it.

### 4. What this ADR does not decide

**It does not authorise reading `refresh_tokens` without a tenant.** ADR-0004:77 states that a caller with no tenant "operates only on global tables"; `refresh_tokens` is tenant-owned, is not on `GLOBAL_TABLES` (`packages/database/src/schema.ts:36`), and `withGlobal` cannot name it (`schema.ts:47`). Migration `005:646-653` defers this to W1-002 and to `docs/WAVE_1_REGISTER.md`, where it is recorded as **D-W1-004** with three conditions. **A companion ADR must be Accepted before any code performs the pre-tenant lookup this index exists to serve**, and it must decide the mechanism explicitly — a narrow `SECURITY DEFINER` resolver returning only `(tenant_id, token_id)`, a distinct pre-authentication role with its own policy, or another — together with rate limiting that does not depend on knowing the tenant, and a rule that a `23505` or `DETAIL` from either path is never surfaced or logged.

The index may land ahead of that ADR because its shape is determined under every candidate mechanism: each of them performs a lookup by hash alone. The one alternative that would not — a tenant hint in the cookie — is independently excluded by ADR-0009:60.

## Consequences

**Accepted cost.** One globally unique index exists on a tenant-owned table. Tenants share a namespace in `refresh_tokens.token_hash`, and a `23505` there is information about another tenant. Measured, as `finsoft_app` under RLS with tenant A's context and a hash belonging only to tenant B:

```
SELECT ... WHERE token_hash = <B's hash>   ->  0 rows
INSERT ... token_hash = <B's hash>         ->  23505 duplicate key value
```

The row is invisible and still collides, because **unique index enforcement is not subject to row level security**.

**It is unreachable SO LONG AS CONDITION 5 HOLDS — which is a review gate, not a mechanism.** An earlier draft of this paragraph said flatly "it is unreachable: the presentation path is a `SELECT`, not an `INSERT`, so no caller can drive a collision." That is true of the *refresh endpoint* and false of the *table*: `finsoft_app` holds `INSERT` on `refresh_tokens`, and the login path writes a `token_hash` the application computed. Nothing in the schema forces that value to come from a CSPRNG. If a future minter is ever weakened — a truncated value, a counter, a value derived from something a caller influences — the oracle becomes live, and no constraint in this ADR would notice.

Condition 3 (write-once) does not close this: it governs `UPDATE` and says nothing about `INSERT`. Isolation on that one lookup therefore rests on 256 bits of entropy rather than on RLS, and on a human check that the entropy is real. That is a genuine weakening of ADR-0004's backstop on one path, recorded here rather than buried in a migration comment.

**Positive.** The exemption for surrogate primary keys is stated at LEVEL 1 instead of inferred from a test comment. The criterion is a necessity test rather than a description of how values are produced, so it cannot be widened by finding another column that happens to be random. Four of the five conditions fail the build rather than a reviewer's memory.

**Negative.** An allowlist is a list, and lists grow. Mitigated by (N) being the gate and by each entry requiring an ADR citation: adding a name means arguing in an ADR that a tenant-scoped constraint is unenforceable at the point of use, which is a much narrower claim than "this value is random".

## Alternatives considered

**Widen the test's exemption without an ADR.** Rejected. It sets the meaning of a LEVEL 1 rule by editing a LEVEL 3 file, which is the inversion CLAUDE.md's authority table forbids, and it would compound the existing instance rather than fix it.

**Edit ADR-0003:28 in place.** Not available. [README](README.md) §4: Accepted ADRs are superseded, never edited.

**Exempt "system-generated" columns generally.** Rejected. Not mechanically checkable, and satisfied by any column with a `DEFAULT`. It also licenses the weak case — a random value with no pre-tenant lookup behind it — which is precisely the case this ADR refuses.

**A global `token_directory(token_hash → tenant_id)` table, leaving `refresh_tokens` scoped by tenant.** This would dissolve the exemption entirely: uniqueness would live on a global table, where ADR-0003:28 does not apply. Rejected because it puts a credential-derived value on a table with no RLS, readable before authentication — a worse blast radius than the index it avoids — and creates a two-table consistency obligation on the authentication path, where a partial write means a token that exists in one table and not the other. The exemption is cheaper and more honest than the workaround.

**A tenant hint in the refresh cookie, enabling `(tenant_id, token_hash)`.** Rejected. ADR-0009:60 forbids taking `tenant_id` from a cookie other than the session, and ADR-0009:61 gives the reason: every defence below the guard takes the tenant as input and verifies rows against it, so an attacker-supplied tenant is enforced faithfully. It also leaves the multiplicity problem in §3 unsolved.
